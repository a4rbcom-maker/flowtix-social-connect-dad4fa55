## R1: إيش الـ GraphQL responses اللي بتجيب بيانات مش محادثات؟

**القرار**: 4 أنواع من الـ responses لازم نستبعدها.

| النوع | الـ Doc ID | العلامة المميزة | المشكلة |
|-------|-----------|----------------|---------|
| Timeline/Posts | `27774575068828620` | `"timeline_list_feed_units"` | بيجيب أسماء صفحات نشرت بوستات، مش ناس تواصلت |
| Profile Switching | `27050123717934044` | `"profile_for_intent_switching"` | بيجيب صفحة البروفايل نفسه |
| CRM Contact Detail | `27615938851434506` (detail variant) | `"retrieve_biz_crm_contact"` | بيجيب جهة اتصال CRM مفهاش محادثة حقيقية |
| Page Profile | `27774575068828620` | `"id":"100063921794373"` (page ID) | بيجيب البيدج نفسها |

**البدائل المرفوضة**:
- الاعتماد على `__typename` بس: مش كافي لأن في كائنات كتير مفهاش `__typename` أساساً
- الاعتماد على `doc_id` بس: doc_id بيتغير من فيسبوك كل فترة
- فلترة الأسماء بعد الاستخراج: تصفي الأعراض مش السبب

## R2: إزاي نحدد إن الـ response ده Messenger ولا لأ؟

**القرار**: فحص 3 علامات في response text + postData.

الـ response يُعتبر Messenger إذا **أي شرط** من دول تحقق:
1. `postData` يحتوي على `"thread"` أو `"inbox"` أو `"message_thread"` (موجود حالياً)
2. Response text يحتوي على `"retrieve_biz_crm_contact"` مع `"shared_attributes"` (ده query جهة اتصال من inbox)
3. Response text يحتوي على `"thread_key"` أو `"last_message"` (محادثة حقيقية)

**الـ responses المرفوضة قطعاً** (حتى لو فيهم id+name):
- أي response فيه `"timeline_list_feed_units"` → Timeline
- أي response فيه `"profile_for_intent_switching"` → Profile switch
- أي response الـ postData بتاعه مش فيه thread/inbox/message_thread **و** الـ response text مش فيه العلامات فوق

**البديل المرفوض**:
- فحص `doc_id` فقط: doc_id بيتغير، والفيس بوك بيستخدم نفس الـ doc_id لأكثر من Query (زي 27615938851434506 اللي استخدم للـ list query و detail query)

## R3: إزاي نستبعد الأسماء المولدة أوتوماتيكياً؟

**القرار**: exclusion list + pattern matching قبل إضافة الاسم للنتائج.

الأسماء المولدة من فيسبوك (للأجهزة والحسابات المؤقتة) بتتبع نمط معين:
- `Adventurous<Animal><Number>` — مثل "AdventurousRaccoon2824"
- `Playful<Animal><Number>` — مثل "PlayfulGuava970"
- `Shiny<Animal><Number>` — مثل "ShinyCapybara5881"
- أسماء أخرى: `IG <name>`, `WA Not Available`

الإضافة لـ `walkJSON`:
```typescript
const autoGenerated = /^(Adventurous|Playful|Shiny|Happy|Sleepy|Crazy|Funny|Silly|Cool|Super)[A-Z][a-z]+\d+$/;
```

## R4: إزاي نستبعد الصفحات والمؤسسات بدون `__typename`؟

**القرار**: استخدام keyword matching + تحليل `id` prefix.

فيسبوك بيستخدم رقمين مختلفين للـ IDs:
- User IDs: تبدأ بأرقام عادية (5-15 digits)
- Page IDs: ممكن تكون أطول أو تبدأ بأرقام خاصة

لكن الطريقة الأضمن: فحص الاسم نفسه:
- لو الاسم فيه: "News", "Store", "School", "University", "Restaurant", "Cafe", "Airline", "Entertainment", "Recruiting" → استبعاد
- لو الاسم يبدو وكأنه نشاط تجاري (فيه "Co.", "Inc.", "Ltd.", "Store", "Shop", "Boutique") → استبعاد
- لو الاسم يبدو وكأنه مؤسسة تعليمية (مدرسة/جامعة/أكاديمية) → استبعاد

**البديل المرفوض**: الاعتماد على `__typename` فقط — في كائنات كتير مفهوش `__typename` في الـ GraphQL response.

## R5: إزاي نضمن عدم تكرار الأسماء؟

**القرار**: المرحلة الأولى — استبعاد self-reference. المرحلة الثانية — dedup بالـ ID.

1. **Self-reference exclusion**: الـ excludeId اللي هو page ID يمنع الصفحة نفسها. بس المشكلة أن نفس الشخص (صاحب الصفحة) ممكن يظهر ب ID تاني كـ user شخصي. الحل: استبعاد أي اسم يطابق اسم الصفحة مع أي ID.
2. **Dedup بالـ ID**: الموجود حالياً (seen set) — بس لازم نضيف كمان dedup بـ الـ name عشان لو نفس الشخص ظهر بأكثر من ID.

## R6: هل الفلاتر دي تؤثر على أداء الاستخراج؟

**القرار**: لا. الفلاتر بسيطة (string check + regex) وبتشتغل في O(n). تأثير الأداء لا يُذكر.

فلترة الـ response قبل `deepParse` بتقلل عدد الـ responses اللي بتتمر عليها فعلياً، فده ممكن يحسن الأداء مش يبطئه.
